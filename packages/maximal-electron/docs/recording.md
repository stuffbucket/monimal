# Screen recordings

This repository can drive itself and record the result. The output is an mp4
that plays anywhere, cut from real frames of the real application.

Nothing here is a mock. The window in the video is the window `npm start`
opens. The terminal in it runs a real shell. The overlay in it talks to a real
model through the real approval gate.

```bash
npm run package        # the recorder drives the built bundles
npm run record         # every timeline
npm run record -- --grep workflow
```

Output lands in `demo/`.

## Why this exists

A reference template has to show what it is. A screenshot cannot show an agent
taking a turn, and a hand-made screen capture goes stale the moment the
interface moves.

A recorded timeline does not go stale. It is code, it runs in continuous
integration terms, and a change that breaks the interface breaks the recording.

## Two steps, not one

Recording is **capture** then **compose**, with a durable artefact between.

```
capture  ──>  demo/takes/<name>/        ──>  compose  ──>  demo/<name>.mp4
(minutes,     take.json                       (seconds,
 drives app)  frames/frame-000001.jpg          pure)
              cards/<seq>.png
```

This is the whole design. Holds used to be wall clock waits inside the
recording, so a 107 second video cost 107 seconds of driving. Changing one beat
meant driving a real `claude` and a real model round trip again. Timing is data
now.

Measured on this repository: a capture is about 45 seconds, and a re-cut is
about 6.

A **take** is raw material. Every frame that was captured, stamped and grouped
by sequence, with the cards beside it. It is large, it is not tracked, and it
is regenerated by `npm run record`.

An **edit** is the cut. Which sequences, in what order, how long each holds,
where it freezes. Small, tracked, and edited by hand.

## Re-cutting

```bash
npm run compose                 every edit that has a take
npm run compose -- workflow     one of them
```

An edit is JSON:

```jsonc
{
  "take": "workflow",
  "output": "demo/stuffbucket-workflow.mp4",
  "clips": [
    { "seq": "fleet", "hold": 7 },
    { "seq": "inspector", "hold": 8, "freezeAt": "approval-shown" },
    { "seq": "terminal", "hold": 10, "card": false },
    { "seq": "repaints", "hold": 11, "optional": true }
  ]
}
```

| Field | Meaning |
| --- | --- |
| `seq` | Sequence id. An unknown id fails, and names the ids that exist. |
| `hold` | Seconds on the held frame. Defaults to `MIN_HOLD_SECONDS`. |
| `freezeAt` | Mark to hold on. Defaults to the last frame. |
| `from`, `to` | Marks bounding the played range. `start` and `end` always work. |
| `card` | `false` hides it. `{ placement }` moves it. |
| `optional` | Tolerate a sequence the take does not hold. |

A clip may appear more than once, and in any order.

## Marks

A **mark** is a named instant a sequence chose to remember. `drive` gets
`mark(label)`, and an edit freezes on the name:

```ts
await expect(shell.locator('[data-testid="approval"]')).toBeVisible();
mark('approval-shown');
```

Freezing by name rather than by second stays correct when the next capture
reaches the same moment at a different time.

## Writing a timeline

A timeline is a list of sequences. Each drives the interface; how long the
result is held is the edit's business, not the timeline's.

```ts
sequence({
  id: 'library',
  name: 'A caption in the lower third',
  note: 'An optional second line',
  drive: async ({ shell, mark }) => {
    await shell.click('[data-testid="nav-library"]');
    mark('library-open');
  },
});
```

Use `sequence()` rather than an object literal. It checks the id rules, and a
literal would skip them. Ids are lower case, digits, and dashes, because they
are keys in a JSON file a person edits by hand.

Internal pacing inside `drive` is content and stays. A pause between two tab
clicks, or a typing delay, is part of what the viewer watches. Holds are not.

## The pacing rules

These live in `edit.ts`, which checks them against the edit rather than leaving
it to whoever writes one. Each is easy to shave off and hard to notice until
the video is unwatchable.

| Rule | Value | Why |
| --- | --- | --- |
| `MIN_HOLD_SECONDS` | 5 | Time on a still screen. Shorter reads as a slideshow. |
| `SETTLE_SECONDS` | 1.2 | The one that is still a real wait. See below. |
| `GAP_SECONDS` | 1.2 | Clips never butt up against each other. |
| `DIP_SECONDS` | 0.35 | The fade across each join. |
| `MIN_TOTAL_SECONDS` | 30 | Give a viewer time to take it in. |
| `MAX_FINAL_PAD_SECONDS` | 12 | A cap, so padding cannot rescue a stub. |

`edit.ts` rejects an edit that cannot reach the duration floor, before compose
writes a frame.

`SETTLE_SECONDS` is the only one that is still a real wait during capture. It
has to be. The interface is mid-reaction when `drive` returns, and a frame that
was never captured cannot be recovered later. Compose applies every other
number, so breaking one costs six seconds to find and six to fix.

One rule the code cannot enforce. When the point of a sequence is a visible
change, make the change happen **early** in `drive`. Freezing helps here, but
the frames still have to exist.

## Why the capture goes through the debugger

`page.screenshot` reads the operating system surface. A recording run parks its
windows off the side of the display. An occluded window gets no frames from the
macOS compositor, so the call blocks until its timeout.

`Page.startScreencast` reads the renderer instead, which does not care what is
in front. Measured here it delivers about 23 frames a second while the
interface moves, against about 3 a second for a screenshot loop.

It also emits nothing while the screen is still. That is correct. A held frame
carries the whole pause, and compose gives it the duration the edit asks for.

## Why the timing is not a frame rate

A screencast emits at irregular intervals. The obvious fix is an `ffmpeg`
concat list with a `duration` per still. That is wrong.

The concat demuxer rounds every duration to the inner demuxer time base, which
for a still is a twenty-fifth of a second. Frames arriving at about 30 a second
each rounded up to 40 milliseconds. A 38 second timeline came out as 51 seconds
of slow motion.

So compose writes each clip as a numbered sequence at the output frame rate,
using symbolic links rather than copies. A minute of video is 1800 ticks over
roughly 900 distinct stills.

## Colour

The stills are JPEG, which is full range. Carrying that through tags the mp4 as
`yuvj420p`, and players disagree about what to do with that tag. The same file
comes out washed out in one player and crushed in another.

The filter graph converts with `in_range=full:out_range=tv`. That writes a
plain `yuv420p` limited range stream, and it puts black at the level the fade
expects.

## What the recorder checks

A recording that produces a broken file must fail, not ship. After the encode
the recorder probes the output and rejects it when:

- the duration is under `MIN_TOTAL_SECONDS`,
- the codec is not `h264`.

Close the application with `closeApp` from `e2e/harness.ts`. A crash during
teardown happens after the last frame, so a plain close would report a clean
recording over a process that aborted.

## Requirements

- `ffmpeg` and `ffprobe`. Nothing installs them for you. See below.
- A packaged build. The recorder drives `.vite/`, for the reason in
  `AGENTS.md`: the `EnableNodeCliInspectArguments` fuse stops Playwright
  attaching to a packaged binary.
- `STUFFBUCKET_E2E_VISIBLE=1` to watch a run. It is slower, and it takes over
  the desktop for the length of the timeline.

## Finding the encoder

`src/main/native/ffmpeg.ts` owns the search. It is the only copy of these
rules, and it imports no `electron`, so the recorder and the application both
use it.

The order for each tool:

1. `FFMPEG` or `FFPROBE`, when set. An explicit value wins outright. Searching
   past a bad override would hide the typo.
2. Known install directories for the platform. On macOS that is Homebrew on
   Apple Silicon, then Homebrew on Intel, then MacPorts, then the system.
3. The bare name, resolved through `PATH`.

Step 2 exists because a graphical application on macOS does not inherit the
shell `PATH`. The window server launches it. So a `brew` install that works in
a terminal is invisible to the packaged application.

**The check runs the binary.** It calls `-version` and waits for exit code 0.
Asking whether a file exists is not the same question. A broken symlink, the
wrong architecture, or a missing execute bit all satisfy a stat. Each one then
fails inside the encode.

## When it is not installed

The recording stops before it launches anything, and says so:

```
ffmpeg and ffprobe are not installed. Recording needs them to encode the video.

  brew install ffmpeg

Then try again. Set FFMPEG and FFPROBE if they are somewhere unusual.
```

Three rules behind that message:

- **Nothing is downloaded or installed on the user's behalf.** An encoder is an
  executable, not data. Fetching one after install is a different risk class
  from fetching model weights, which `llama.ts` does. A truncated model fails
  loudly on load. A substituted binary does not.
- **One command, not a menu.** Somebody blocked on this wants a line to paste.
- **Say that the fix is to run it again.** Without it the reader has to guess
  whether the application is now in a broken state.

The check lives in `e2e/demo/global-setup.ts`, which Playwright runs once
before any worker starts. It pins the paths it verified into the environment,
so the encoder that runs is the one that was tested.

## Fixture data

`e2e/fixtures/demo-shell/runs.ts` holds the agent fleet the video shows, beside
the components that render it. The whole fixture is a separate renderer entry
point, and `STUFFBUCKET_DEMO` selects it: the main process loads that bundle
instead of the product's.

`forge.config.ts` keeps the fixture bundle out of the package, and
`npm run verify:package` fails if it ever appears. The fixture is reachable from
a checkout and not from an installed application.

Nothing else in the application behaves differently. The terminal, the overlay,
the agent, and the approval gate are all the production code paths, and the
chrome around them is the product's own `ShellLayout`, `NavRail`, and
`TerminalTabs` rather than a copy.

## Cards

Capture renders cards to transparent images, and compose lays them over the
video. Capture used to inject them into the page while recording, which burned
them into the frames. Moving one, hiding one, or changing where it sat then
meant driving the application again.

A browser still draws them rather than the encoder. `drawtext` cannot do the
rounded corner, the hairline border, or the drop shadow.

Three things about that rendering are not obvious, and each one produced a
visible defect first:

- **The card gets its own window.** Clearing the page background is not enough,
  because the shell window is opaque by construction. Every capture came back
  on a solid rectangle, which reads as a dark box around the card rather than a
  shadow. A throwaway `transparent: true` window has real alpha.
- **The rules go in a `<style>` block, not a `style` attribute.** The font stack
  contains `"Segoe UI"`, and those double quotes close an HTML attribute early.
  The browser drops everything after them, which cost a card its colour and its
  typeface.
- **The card is inset by the margin it needs.** The image carries a transparent
  border wide enough for the shadow. Sitting the card 40 pixels from the edge
  while asking for 64 pixels of margin clamped the capture, and the card then
  sat 24 pixels off in the finished video.

Changing the wording needs a capture, because the card pass runs there.
Position, order, timing, and show or hide are all edits.

## Disk

A take is roughly 100 to 175 MB. There is one directory per timeline name,
overwritten on each capture, so the total stays bounded rather than growing on
every run. `demo/takes/` is not tracked. Delete it freely; `npm run record`
makes it again.
